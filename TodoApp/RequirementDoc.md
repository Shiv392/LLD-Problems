# 📝 Todo Management System — Requirements

> **Difficulty:** Easy → Intermediate  
> **Type:** Low-Level Design (LLD) Exercise  
> **Language:** Java  
> **Version:** 1.0

---

## 1. 🎯 Client Requirement

The client wants a simple **Todo Management System** that allows a user to create, view, update, complete, reopen, and delete personal todo items.

Each todo must have a unique ID, a name, a description, a status, and a creation timestamp.
Whenever a new todo is created, its status must automatically be set to `UNDONE`.
The application should make it easy for the user to keep track of pending and completed work.

---

## 2. 👤 User & System Scope

- The system supports **one user** for this version.
- The user can manage multiple todo items.
- Each todo is independent of other todos.
- Data will be stored in memory for this LLD exercise.
- The storage layer should be replaceable so that a database can be introduced later.

### Out of Scope

To keep the exercise at Easy → Intermediate level, the following features are not required:

- User registration and login.
- Multiple users or shared todo lists.
- Due dates, reminders, or notifications.
- Categories, tags, priorities, or subtasks.
- Recurring todos.
- File attachments.
- Advanced search and filtering.
- Database integration or cloud deployment.

---

## 3. 📦 Todo Entity

Every todo item must contain the following fields:

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | `UUID` | Yes | Unique identifier generated by the system |
| `name` | `String` | Yes | Short title of the todo |
| `description` | `String` | Yes | Details about what needs to be done |
| `status` | `TodoStatus` | Yes | Current state: UNDONE or DONE |
| `createdAt` | `LocalDateTime` | Yes | Todo creation timestamp |
| `updatedAt` | `LocalDateTime` | Yes | Last modification timestamp |

### Todo Status

```java
public enum TodoStatus {
    UNDONE,
    DONE
}
```

### Default Values and Rules

- `id` must be generated automatically by the system.
- `status` must default to `UNDONE` when a todo is created.
- `createdAt` must be assigned automatically.
- `updatedAt` must initially be the same as `createdAt`.
- Whenever todo details or status change, `updatedAt` must be refreshed.
- The user cannot directly modify `id` or `createdAt`.

---

## 4. ⚙️ Functional Requirements

### FR-01: ➕ Create a Todo

The user should be able to create a new todo by providing:

- Name
- Description

**System Behaviour:**

1. Validate the provided name.
2. Generate a unique ID.
3. Set status to `UNDONE` automatically.
4. Set `createdAt` and `updatedAt` automatically.
5. Save the todo.
6. Return the newly created todo.

**Acceptance Criteria:**

- Every todo must have a unique ID.
- Initial status must always be `UNDONE`.
- Timestamps must be generated by the system.
- The user cannot choose the initial status.

### FR-02: 📋 View All Todos

The user should be able to retrieve all existing todos.

**System Behaviour:**

- Return all existing todos.
- If no todos exist, return an empty collection.
- Display todos in creation order, oldest first.

### FR-03: 🔍 View Todo by ID

The user should be able to retrieve a particular todo using its ID.

**System Behaviour:**

- If the ID exists, return the matching todo.
- If the ID does not exist, return a meaningful `TodoNotFoundException` or equivalent not-found result.

### FR-04: ✏️ Update Todo Details

The user should be able to update:

- Name
- Description

**System Behaviour:**

1. Find the todo using its ID.
2. Update the editable fields.
3. Refresh `updatedAt`.
4. Preserve the existing ID, `createdAt`, and status.

**Acceptance Criteria:**

- Updating a todo must not generate a new ID.
- Updating details must not reset its status.
- An unknown ID must produce a not-found result.

### FR-05: ✅ Mark Todo as Done or Undone

The user should be able to change the status of a todo.

**System Behaviour:**

- The user can mark an `UNDONE` todo as `DONE`.
- The user can reopen a `DONE` todo by changing it to `UNDONE`.
- Refresh `updatedAt` whenever the status changes.
- If the requested status is already set, leave the todo unchanged.

### FR-06: 🗑️ Delete a Todo

The user should be able to delete a todo using its ID.

**System Behaviour:**

- Delete the matching todo if it exists.
- If the ID does not exist, return a meaningful not-found result.
- A deleted todo must no longer appear in the all-todos list or be retrievable by ID.

---

## 5. 🧪 Validation Rules

| Input | Validation |
|---|---|
| Name | Must not be null, empty, or blank |
| Description | Must not be null, empty, or blank |
| ID | Must identify an existing todo for view, update, status change, or delete |
| Status | Must be one of the defined `TodoStatus` values |

**Additional Rules:**

- Leading and trailing whitespace should be trimmed.
- Invalid input should produce a meaningful validation error.
- User-provided values must not be accepted for system-managed fields such as `id`, `createdAt`, and `updatedAt`.

---

## 6. 🛡️ Non-Functional Requirements

1. **Maintainability:** Keep business logic separate from storage logic.
2. **Extensibility:** Storage implementation should be replaceable without rewriting the core business logic.
3. **Reliability:** Todo IDs must be unique, and invalid operations must fail clearly.
4. **Simplicity:** Avoid unnecessary design patterns and abstractions.
5. **Testability:** Core operations should be testable independently.

---

## 7. 🚨 Expected Error Scenarios

The system should handle these cases gracefully:

- Creating a todo with a blank name.
- Creating a todo with a blank description.
- Viewing a todo with an unknown ID.
- Updating a todo with an unknown ID.
- Changing the status of an unknown todo.
- Deleting a todo with an unknown ID.

Use meaningful exceptions or result handling. Do not silently ignore invalid requests.

---

## 8. 🧩 Suggested LLD Responsibilities

These are design hints, not mandatory class names. You should decide the final class structure yourself.

| Responsibility | Description |
|---|---|
| Todo Model | Stores todo data and its state |
| Todo Status | Defines allowed todo states |
| Todo Service | Handles use cases and business rules |
| Repository / Storage | Handles saving, finding, listing, updating, and deleting todos |
| Validation / Exceptions | Handles invalid input and missing todo scenarios |

**Design Expectation:**

The service should depend on a storage abstraction rather than directly depending on a specific in-memory collection.

For this exercise, an in-memory repository is sufficient.

---

## 9. ✅ Definition of Done

The first version is complete when:

- [ ] A user can create a todo.
- [ ] A new todo automatically gets `UNDONE` status.
- [ ] A user can view all todos.
- [ ] A user can view a todo by ID.
- [ ] A user can update its name and description.
- [ ] A user can mark a todo as `DONE`.
- [ ] A user can reopen a todo as `UNDONE`.
- [ ] A user can delete a todo by ID.
- [ ] Invalid inputs and unknown IDs are handled clearly.
- [ ] `createdAt` remains unchanged after creation.
- [ ] `updatedAt` changes when details or status are modified.

---

## 10. 🎓 LLD Exercise Constraints

To keep this exercise at **Easy → Intermediate** level:

- Use Java and object-oriented design.
- Use `UUID` for todo IDs.
- Use `LocalDateTime` for timestamps.
- Use an enum for todo status.
- Start with an in-memory implementation such as `Map<UUID, Todo>`.
- Keep the design small and readable.
- Do not add database, REST API, authentication, or concurrency handling in this version.

### Suggested Implementation Order

1. Define the `Todo` model and `TodoStatus` enum.
2. Define the repository/storage contract.
3. Implement the in-memory repository.
4. Implement the service operations.
5. Add validation and not-found handling.
6. Write tests for success and failure scenarios.

---

## 🎯 Client's Expected Outcome

A small, reliable Todo Management System that supports the complete CRUD lifecycle and allows a user to track whether each task is pending or completed.
